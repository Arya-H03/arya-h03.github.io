Introduction

IronHammer started as a question: what does a game engine actually look like under the hood?

I have experience working with commercial engines like Unity and Unreal. While I can use them comfortably and work with their built in systems, I always wanted to understand what is actually happening beneath the surface. It is easy to attach a collider component and have collision magically work, but what is that magic, exactly? This project is my attempt to find out by building those systems myself from scratch.

The result is a complete 2D game engine and editor built without any framework or scaffolding, only libraries for windowing, graphics, and UI. Every architectural decision had to be made deliberately, from how thousands of game objects are stored in memory, to how the editor converts between three different coordinate systems. The engine is still actively in development. This page is a record of the systems built so far and the thinking behind them.

Entity Component System

The ECS is the foundation that everything else is built on. Rather than storing game objects as individual classes scattered across memory, IronHammer groups entities that share the same set of components together in one contiguous block, an archetype. Within each archetype, all transforms are packed together, all sprites are packed together, and so on.

This layout, known as Structure of Arrays, means that iterating 10,000 entities to move them is a single sequential read through memory, rather than 10,000 random jumps between objects. Modern CPUs are designed to handle sequential reads efficiently, so the difference in performance is significant and measurable.

  • Archetype Storage: Entities sharing the same set of components are grouped into a single contiguous memory block. Adding or removing a component moves an entity to the correct group automatically.
  • Component Self Registration: Every component registers itself with the engine before the program starts via a REGISTER_COMPONENT macro. This lets the engine construct, destroy, save, and display any component through a uniform interface, without knowing the specific type at the call site.
  • Query System: Systems declare what components they need upfront. The engine pre filters matching entity groups at startup, so at runtime there is no searching, just a flat loop over pre validated data.
  • Deferred Changes (CommandBuffer): Structural changes like adding or removing components are queued during the frame and applied after all systems finish, preventing the kind of mid loop corruption that would otherwise be very difficult to debug.
  • Generation Safety: Every entity carries a generation counter alongside its ID. When an entity is destroyed and its slot is reused, the counter increments. Any old reference to that entity will fail validation automatically, no dangling pointers, no silent bugs.

Custom Memory Allocators

Most programs rely on the operating system to hand out and reclaim memory, a process that works well in general but has measurable overhead when done thousands of times per frame. IronHammer implements three purpose built allocators that pre claim large blocks of memory up front and manage them internally, keeping allocations fast and predictable.

  • Templated Slab Allocator: A type safe, template driven allocator that manages a growable list of fixed size slabs on the heap. Each slab holds SlabSize objects of type T and tracks free slots using a 64 bit integer bitset, finding the next available slot reduces to a single CPU instruction (std::countr_zero). Supports both single object and full array allocation. Deallocated memory is returned to its originating slab and made immediately available for reuse, keeping fragmentation minimal. When all existing slabs are full, a new one is appended automatically.
  • Type Erased Slab Allocator: Functionally similar to the Templated Slab Allocator but operates without compile time type information. Rather than being dependent on a type, it accepts an element size at construction and allocates raw 64 byte aligned memory blocks accordingly. A linked free list is added directly into the slab slots themselves, so no external bookkeeping structure is needed. Typed access is restored at the call site via reinterprate casting.
  • Type Erased Block Allocator: A simpler, array only variant of the type erased approach designed specifically for archetype component storage. Rather than allocating individual objects, it hands out entire contiguous blocks of memory, one block per component array per chunk. Individual element removal is handled not by deallocation but by a swap and pop: the removed element is overwritten by the last element in the array, keeping the block fully packed at all times. Once enough removals have accumulated and a block becomes empty, it is returned to the free list and recycled for future chunks.

// Free slots tracked as bits: 1 = free, 0 = used.
size_t FindFirstFreeBit()
{
    if constexpr (wordCount == 1)
    {
        if (bitSet.single != 0)
        {
            return std::countr_zero(bitSet.single);
        }

    }
    else
    {
        for (size_t i = 0; i < wordCount; ++i)
        {
            if (bitSet.multiple[i] != 0)
            {
                return (i * 64) + std::countr_zero(bitSet.multiple[i]);
            }
        }
    }
}

T* Allocate()
{
    // Find or create a slab with space
    if (currentSlabIndex == SIZE_MAX || slabs[currentSlabIndex].freeCount == 0)
    {
        currentSlabIndex = FindFreeSlab();
        if (currentSlabIndex == SIZE_MAX)
        {
            slabs.emplace_back();
            currentSlabIndex = slabs.size() - 1;
        }
    }

    auto&  slab      = slabs[currentSlabIndex];
    size_t freeIndex = slab.FindFirstFreeBit();
    slab.SetBitToZero(freeIndex);
    --slab.freeCount;
    return &slab.blocks[freeIndex];
}

void DeAllocate(T* ptr)
{
    auto [slabIndex, blockIndex] = LocateBlock(ptr);
    slabs[slabIndex].ResetBitToOne(blockIndex);
    ++slabs[slabIndex].freeCount;
    currentSlabIndex = slabIndex;
}

  • Type Erased Slab Allocator 

    
struct Slot
{
    Slot* nextFreeSlot;       // free list pointer
    alignas(64) char data[1]; // actual object data lives here
};

void* InternalAllocate()
{
    if (m_freeList == nullptr) AllocateNewSlab();

    Slot* slot = m_freeList;
    m_freeList = m_freeList->nextFreeSlot; // pop from free list
    return slot->data;
}

void InternalDeallocate(void* ptr)
{
    // Recover the Slot header from the data pointer
    Slot* slot = reinterpret_cast<Slot*>(
        reinterpret_cast<char*>(ptr) - offsetof(Slot, data));

    slot->nextFreeSlot = m_freeList;  // push back onto free list
    m_freeList = slot;
}

template <typename T, typename... Args>
T* Allocate(Args&&... args)
{
    void* memory = InternalAllocate();
    return new (memory) T(std::forward<Args>(args)...);
}

template <typename T>
void Deallocate(T* obj)
{
    obj->~T();
    InternalDeallocate(obj);
}

// Allocates entire contiguous blocks, one per component array per chunk.
// Blocks are 64 byte aligned so arrays land exactly on cache line boundaries.
void AllocateNewBlock()
{
    void* newBlock = operator new(
        m_dataPerBlock * m_dataSize,
        std::align_val_t(64)    // cache line aligned
    );
    m_allBlocks.push_back(newBlock);
    m_freeBlocks.push_back(newBlock);
}

void* AllocateBlock()
{
    if (m_freeBlocks.empty()) AllocateNewBlock();

    void* freeBlock = m_freeBlocks.back();
    m_freeBlocks.pop_back();
    return freeBlock;
}

void DeallocateBlock(void* ptr)
{
    m_freeBlocks.push_back(ptr);
}

Physics Pipeline

The physics system runs in three separate stages each frame. Splitting it this way keeps each stage focused and independently testable. A design decision that paid off significantly during debugging.

  • Broad Phase Spatial Grid: Checking every object against every other object for collision is impractical at scale, 200 objects would mean 40,000 checks every frame. Instead, the world is divided into a grid of small cells. Objects only need to be checked against others that share the same cell, cutting the number of checks down dramatically.
  • Narrow Phase Precise Contact: The candidates from the broad phase are tested exactly. A key detail here: rather than just checking the current frame's overlap, the engine also looks at where each object was last frame to determine the correct push direction. This prevents the jittery, incorrect collisions that occur when objects meet at a corner.
  • Resolution Impulse Response: Confirmed collisions are resolved by applying an impulse, a velocity correction proportional to each object's mass. Static objects (walls, platforms) are given infinite effective mass, so they absorb nothing and never move.
  • Debug Visualiser: The spatial grid can be visualised at runtime cells light up yellow when one object overlaps them, red when two or more do. This was invaluable for verifying the broad phase worked correctly.

  • Broad Phase Spatial Grid 

    
// Each entity registers into every grid cell its bounds touch.
// Only entities sharing a cell become collision candidates.

for (size_t i = 0; i < chunk.size; ++i)
{
    CCollider&  col = colliders[i];
    CTransform& tr  = transforms[i];

    // Which cells does this entity's bounding box overlap?
    Vect2<int> topLeft  = ((tr.position + col.offset - col.halfSize) / m_cellSize).Floor();

    Vect2<int> botRight = ((tr.position + col.offset + col.halfSize) / m_cellSize).Ceil();


    for (size_t r = topLeft.y; r < botRight.y; ++r)
    {
        for (size_t c = topLeft.x; c < botRight.x; ++c)
        {
            m_grid[r * m_cellPerRow + c].overlapingEntities.push_back(chunk.entities[i]);
        }
    }
}

Rendering System

At the beginning of this project the one area where I felt most lacking was graphics programming. Although I'm keen on learning this topic from scratch, With all the other things that I had to learn and implement for the first time, I decided to go with an open source library to handle graphics. I'm already thinking about upgrading the engine to 3D at a later date and that will be point where I certainly try to implement my own libraries. However, that's out of scope currently. With that out of the way, I've decided to use SFML's graphics module which is built on top of OpenGL. This will allow simple rendering of sprites, shapes, lines and texts. The key point is to ensure efficient rendering when entity count grows and draw calls increase. The rendering system avoids issuing one per entity by accumulating all geometry into a single vertex array and flushing it in one call, or as few calls as possible. For sprites, a new flush only happens when the texture changes. For shapes and collider wireframes, flushes are triggered by a configurable vertex budget.

Sprite geometry is computed manually per entity: rotation is applied using a precomputed cosine/sine pair, UV coordinates are mapped from each sprite's texture rectangle, and the result is written directly into the batch. No intermediate objects, no allocations per frame.

void RenderSystem::AddSpriteToBatch(const CSprite& csprite, const CTransform& ctransform, sf::VertexArray& batch)
{
    float width = csprite.size.x * ctransform.scale.x;
    float height = csprite.size.y * ctransform.scale.y;
    float halfWidth = width / 2.0f;
    float halfHeight = height / 2.0f;

    Vect2f center = ctransform.position;

    float rad = ctransform.rotation * (float) M_PI / 180.0f;
    float cosRad = std::cos(rad);
    float sinRad = std::sin(rad);

    // Rotate a local space offset into world space
    auto Rotate = [&](float x, float y) { return sf::Vector2f(center.x + x * cosRad - y * sinRad, center.y + x * sinRad + y * cosRad); };

    sf::Vector2 topLeft = Rotate(-halfWidth, -halfHeight);
    sf::Vector2 topRight = Rotate(halfWidth, -halfHeight);
    sf::Vector2 bottomRight = Rotate(halfWidth, halfHeight);
    sf::Vector2 bottomLeft = Rotate(-halfWidth, halfHeight);

    float u1 = csprite.textureRect.position.x;
    float v1 = csprite.textureRect.position.y;
    float u2 = csprite.textureRect.position.x + csprite.textureRect.size.x;
    float v2 = csprite.textureRect.position.y + csprite.textureRect.size.y;

    sf::Vector2f uvTopLeft(u1, v1);
    sf::Vector2f uvTopRight(u2, v1);
    sf::Vector2f uvBottomRight(u2, v2);
    sf::Vector2f uvBottomLeft(u1, v2);

    batch.append(sf::Vertex(topLeft, csprite.color, uvTopLeft));
    batch.append(sf::Vertex(topRight, csprite.color, uvTopRight));
    batch.append(sf::Vertex(bottomRight, csprite.color, uvBottomRight));

    batch.append(sf::Vertex(topLeft, csprite.color, uvTopLeft));
    batch.append(sf::Vertex(bottomRight, csprite.color, uvBottomRight));
    batch.append(sf::Vertex(bottomLeft, csprite.color, uvBottomLeft));
}

Multithreaded Debug Logger

When something goes wrong in a game, knowing exactly where in the code it happened saves hours of debugging. IronHammer's logger captures a full stack trace on every log call, a record of every function call that led to that point. The problem is that translating raw memory addresses into readable function names and file paths is exteremly slow. Doing it on the game thread would cause a noticeable frame drop on every single log.

The solution is to split the work across two threads. The game thread captures the raw trace instantly and pushes it to a queue. A dedicated background thread picks it up, resolves the symbols at its own pace, and places the finished result in a buffer. At the end of each frame, the main thread moves everything from the buffer into the log window, with no lock held during the actual ImGui rendering.

  • Game Thread: Captures the stack trace and pushes a pending message. Cost is a single mutex lock and a condition variable notification.
  • Logger Thread: Resolves symbols using backwards-cpp, cleans up C++ name mangling, and writes finished log entries to a double buffer. Sleeps when idle, zero CPU overhead between frames.
  • Main Thread: Calls FlushLogs() once per frame to move resolved entries into the read queue. The ImGui log window then reads freely with no lock held.
  • Pre cached Strings: Each log entry pre builds its display string at construction time so that the log window renders with zero string formatting work per frame.

// The logger thread sleeps until work arrives, resolves
// the expensive stack trace off the game thread, then
// writes the finished result to the buffer queue.

m_loggerThread = std::thread([]()
{
    while (true)
    {
        std::unique_lock lock(m_pendingLogsMutex);
        m_cv.wait(lock, [] {
            return !m_pendingLogMesssageQueue.empty() || !m_loggerRunning; });

        if (!m_loggerRunning&& m_pendingLogMesssageQueue.empty()) break;

        while (!m_pendingLogMesssageQueue.empty())
        {
            PendingLogMessage msg = std::move(m_pendingLogMesssageQueue.front());

            m_pendingLogMesssageQueue.pop();
            lock.unlock();

            // Expensive fully off the game thread
            auto traces = ResolveStackTrace(msg.stackTrace);
            {
                std::lock_guard bufLock(m_logMessagesMutex);
                m_logMessageQueueBuffer.emplace_back( msg.message, msg.time, traces, msg.color, msg.logType);
            }
            lock.lock();
        }
    }
});

Editor & Tooling

IronHammer ships with a fully integrated editor built using Dear ImGui. The goal was a complete authoring environment where game worlds can be built, simulated, modified, and saved without leaving the application. All editor panels share a single context object. No global state, no singletons, passed by reference to every panel that needs it.

  • Viewport: The game world renders into a texture that is displayed inside the editor window. Clicking and dragging within that view requires converting between three different coordinate systems world space, texture pixel space, and screen space which the Viewport class handles.
  • Transform Gizmo: Selecting an entity in the editor displays interactive handles directly over it in the viewport. Dragging the center moves the entity freely. Dragging an arrow constrains movement to a single axis. A mode toggle switches between Translate and Scale.
  • Component Inspector: Every component exposes its fields, position, size, color, speed as editable controls in the inspector panel. A reset button and a remove button are provided for every component through a shared template, so no duplicated UI code exists across components.
  • Prefab System: Entities are saved as JSON template files. Dragging a template from the asset panel into the viewport instantiates it at the cursor position, with optional grid snapping. The entity template can be edited and re-saved from the inspector without touching any code.
  • Play / Edit Mode: The engine maintains two separate worlds simultaneously. The editor world is never modified during play. Exiting play mode is a single pointer swap back, no rollback, no snapshot logic needed.
  • Log Window: The bottom panel displays real time logs from the background logger, filterable by type (info, warning, error), with expandable stack traces showing the exact file and line number of every log call.

// Three coordinate systems must be bridged correctly:
// World space (Y up), texture pixels (Y down), screen (Y down).
// mapCoordsToPixel handles the Y flip via the SFML view.

inline static ImVec2 WorldToViewportGui(const Vect2f& worldPos)
{
    // World → texture pixel (Y flip handled by SFML view)
    sf::Vector2i texPixel =  m_renderTexture->mapCoordsToPixel({ worldPos.x, worldPos.y });

    // Scale from texture resolution to display size
    sf::Vector2u texSize = m_renderTexture->getSize();
    float scaleX = m_viewportImageDrawSize.x / (float)texSize.x;
    float scaleY = m_viewportImageDrawSize.y / (float)texSize.y;

    // Offset to image position in screen space
    return ImVec2(
        m_viewportImagePos.x + (float)texPixel.x * scaleX,
        m_viewportImagePos.y + m_viewportImageDrawSize.y
            - (float)texPixel.y * scaleY);
}
